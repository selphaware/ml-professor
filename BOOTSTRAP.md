**Where you sit in the pipeline:**

| Stage | Runs on | Produces |
|---|---|---|
| **Harness (you, now)** | `fable`, interactive | gate + self-test, `spec.md`, test plan, task plan, `CLAUDE.md`, skill |

**Why this variant exists.** A modelling tool has no right answer on real
data. Its worst bugs produce a plausible number: a leaked feature, a score
computed on training rows, a split that ignores time. Nothing crashes and
nothing looks wrong. So this gate does not judge real-data scores at all. It
manufactures ground truth: synthetic datasets where the correct conclusion is
known by construction, and it checks the tool reaches that conclusion.

**This brief covers phase 1 of five.** The decisions it rests on are recorded
in `docs/DECISIONS.md` as D1 to D22. Read that file. Cite the decision numbers
in `spec.md` wherever the spec restates one. If this brief and that file

## The project

**What it is:**
> ML Professor: a Python package, `mlprofessor`, for ML profiling. A data
> scientist imports one function, passes one table and names a target column,
> and gets back a measurement of how predictable that target is, as pandas
> structures and a JSON file. pandas, numpy and scikit-learn only.
>
> Phase 1 (D1) is the library core: one table, supervised learning, binary
> classification and regression, a random or a time-ordered validation
> scheme, one trustworthy headline number. Later phases add joins with
> grouped validation, unsupervised methods, an HTML report and a Dash app.
> None of those is in scope. Do not plan tasks for them.

**Data source:**
> There is no fixed dataset. The tool accepts any single table, as a pandas
> DataFrame or a path to a CSV file (D3). The data it will meet: financial
> time series (a single series, and panels with many instruments per date),
> general time series, and ordinary structured data with numeric and
> categorical columns.
>
> No real dataset is supplied for this phase and none is in the repo. Do not
> invent one, download one or use a library's bundled dataset. Every dataset
> the gate uses is synthetic and generated by the gate.
>
> - Target: one column, named by the caller.
> - Time: an optional time column, named by the caller as `time_col`. It is
>   never inferred (D7). Accepted forms (D18): a datetime-typed column in a
>   DataFrame, as it is; a numeric column, ordered as numbers; a text column
>   in ISO 8601 form, year first. Anything else stops with a named error.
>   The tool never guesses between day-first and month-first.
> - Repeated entities: possible (a panel). Phase 1 has no grouped scheme. A
>   panel is handled by the time-ordered scheme when `time_col` is given;
>   otherwise the output carries the random-split caveat (D6).
> - Scale target: up to 100,000 rows by 100 columns (D12).
> - No authentication, no network.

**The deliverable:**
> The package folder `mlprofessor`, at `E:\CODE\ml-professor\mlprofessor`.
> **The gate takes one argument: that folder.**
>
> Two public entry points (D2), and nothing else is public:
>
> - The function
>   `mlprofessor.profile(data, target, task="auto", time_col=None, gap=0, profile="full", seed=0, out_dir=None, n_jobs=-1)`,
>   which returns a `ProfileResult`. `n_jobs=-1` uses every core; a positive
>   whole number uses that many (D17).
> - The command line, a thin wrapper over that function:
>   `python -m mlprofessor profile --data file.csv --target col --out dir`,
>   with the options `--task`, `--time-col`, `--gap`, `--profile`, `--seed`
>   and `--n-jobs`.
>
> `ProfileResult` exposes `headline` (a mapping), `models`, `columns`, `rows`,
> `warnings` and `predictions` (pandas DataFrames), `to_dict()` and
> `to_json(path)`.
>
> When an output folder is given, the tool writes two files there:
> `profile.json` and `predictions.csv` (D14). The command line also prints a
> short plain-text summary.
>
> Expected modules inside the package (the builder may reorganise them; only
> the two entry points above are a contract): `__init__.py`, `__main__.py`,
> `cli.py`, `load.py`, `columns.py`, `task.py`, `split.py`, `metrics.py`,
> `preprocess.py`, `models.py`, `leakage.py`, `uncertainty.py`,
> `pipeline.py`, `result.py`.
>
> The package is run from the repo root. Packaging for `pip install` is out
> of scope in phase 1, and the package must not be installed into the venv:
> the gate runs `python -m mlprofessor` with the working directory set to the
> parent of the folder it was given, so the same gate judges the real package
> and each reference implementation in the self-test.

**What "working" looks like to a user:**
> They call `profile(df, target="y")`, or run the command line, and get:
>
> - **Row accounting** (`result.rows`): rows loaded, rows dropped by reason
>   (missing target, missing time value, inside the gap, left out by the fast
>   profile's row cap), training rows, holdout rows.
> - **Column accounting** (`result.columns`): one row per input column, with
>   its role (target, time, feature, excluded), the reason if excluded
>   (constant, id-like, datetime, free text, suspected leak, all missing,
>   unsupported type), and counts of missing, imputed and coerced values.
> - **The task**: classification or regression, and whether it was declared
>   or decided by the rule, with the evidence (the number of distinct values).
> - **The validation scheme**: random or time-ordered, the holdout share, the
>   number of folds, the gap, and under time order the last training
>   timestamp and the first holdout timestamp.
> - **The headline** (`result.headline`): the metric, the chosen model's
>   holdout score, the baseline's name and score, the skill, the interval and
>   its method, and the permutation p-value or the stated reason it is absent.
> - **The models tried** (`result.models`): one row per configuration, with
>   its family, parameters, fold scores, mean and spread, a status (fitted or
>   failed, with the error text) and which one was chosen.
> - **Holdout predictions** (`result.predictions`): `row` (zero-based position
>   in the loaded source), `y_true`, `y_pred`.
> - **Warnings** (`result.warnings`): suspected leaks, a small or one-sided
>   holdout, a date column present with no `time_col` declared, a strongly
>   autocorrelated panel target, a failed model family, values coerced.
> - **A fixed limitations statement**: predictability here means how well
>   these model families did on this data under this validation scheme; low
>   skill is not proof of none; high skill is not proof of cause; a random
>   split is optimistic on ordered or repeated-entity data; look-ahead inside
>   the caller's own features cannot be detected; classification and
>   regression skill are not comparable.
>
> Reconciliation rules, each of which the gate computes for itself:
>
> 1. Rows loaded equal the rows in the source. Rows loaded equal rows dropped
>    (summed over reasons) plus training rows plus holdout rows.
> 2. Every source column appears exactly once in the column accounting.
> 3. `predictions.csv` has one row per holdout row, and each `y_true` equals
>    the target of that row in the source.
> 4. The headline score equals the metric recomputed from `predictions.csv`.
> 5. Every DataFrame on `ProfileResult` equals the matching part of
>    `profile.json`.
> 6. The same seed gives an identical `profile.json` and `predictions.csv`,
>    apart from a `meta.timing` block, which is the only place a clock value
>    may appear.

**How it is measured (methodology):**
> Every line is a recorded decision. Carry them into `spec.md` unchanged.
>
> - **Task types (D4):** binary classification and regression. With
>   `task="auto"`: two distinct target values means classification; a numeric
>   target with more than 20 distinct values means regression; anything else
>   stops with a named error asking the caller to declare the task. A
>   declared task is honoured if the target supports it, and refused with a
>   named error if not (more than two classes; a non-numeric regression
>   target). When the rule picks regression for a target whose values are all
>   whole numbers, the output carries a warning (D21). The task is decided
>   before the fast profile's row cap, so both profiles agree on it (D20).
> - **Headline and baseline (D5):** skill over a baseline, 0 for no better
>   than the baseline and 1 for perfect. Classification: ROC AUC on the
>   holdout, baseline 0.5, skill = 2 x AUC - 1. Regression: skill = 1 - (model
>   squared error / baseline squared error) on the holdout, the baseline
>   predicting the training mean. Accuracy is never the headline. Negative
>   skill is reported as measured.
> - **Validation with no time column (D6):** a 25% holdout split off first,
>   at random from the seed, stratified on the target for classification.
>   Selection by 5-fold cross-validation on the other 75% only (stratified
>   for classification). Refit on that 75%. Score once on the holdout.
> - **Validation with a time column (D7):** the holdout is the latest whole
>   timestamps that together hold at least 25% of the rows, the smallest such
>   set, so rows sharing a timestamp stay on one side. Selection on 5
>   expanding-window folds: the training timestamps are cut into 6 contiguous
>   blocks, and fold k trains on blocks 1 to k and validates on block k+1.
>   `gap` is a number of distinct timestamps removed from the training side
>   immediately before the holdout and before each validation block. If a
>   date column exists and `time_col` is not given, the random scheme is used
>   and a warning is raised. The time column must be in one of the accepted
>   forms (D18); a text column that is not year-first ISO 8601 stops the run.
> - **Regression baseline under time order (D10):** with unique timestamps,
>   the training mean and the previous value (the target `gap + 1` timestamps
>   earlier) are both scored on the holdout; the headline baseline is the one
>   with the lower holdout error and both are reported. With repeated
>   timestamps the baseline is the training mean, with a warning when the
>   per-timestamp mean of the target is strongly autocorrelated over the
>   training period.
> - **Models and budget (D8, D16):** scikit-learn only. A regularised linear
>   model (logistic regression or ridge), a random forest, histogram gradient
>   boosting. Each family has at most 8 configurations including its default,
>   which you pin in `spec.md`: at most 24 configurations and 120
>   cross-validation fits. The forest is at full strength: every tree may
>   draw on all training rows, with no cap on rows per tree. The regression
>   forest considers one third of the features at each split; that is the
>   only departure from scikit-learn's defaults. A dummy baseline is fitted
>   as a reference and is never a candidate.
> - **Inflation (D8):** the chosen model is the one with the best mean
>   cross-validation score (ROC AUC, or squared error for regression); ties
>   go to the earlier family in the order above. The headline is that model's
>   holdout score. Only the chosen model is scored on the holdout.
> - **Alongside the headline (D9):** the spread across folds. Random scheme:
>   a percentile bootstrap 95% interval on the holdout score from 1,000 row
>   resamples, and a permutation p-value from 1,000 shuffles of the holdout
>   targets against the fixed predictions, with no refitting. Time-ordered
>   scheme: a moving-block bootstrap over contiguous holdout timestamps, all
>   rows of a timestamp moving together, block length the cube root of the
>   number of distinct holdout timestamps rounded up; the p-value is absent
>   and the output states why.
> - **Leak rule (D11):** measured on training rows only, a feature column is
>   excluded and listed when it alone predicts the target almost perfectly,
>   or when it is filled in for one class and empty for the other. The
>   cut-offs are yours to set by measurement (see Phase 1). A merely
>   predictive column must not be flagged.
> - **Scale and run time (D12, D16):** up to 100,000 rows by 100 columns; a
>   full run inside 10 minutes on this machine using all cores. Time a full
>   run for both tasks before you pin the grids. If either is over, report it
>   and wait; do not weaken a model to fit. Tables beyond the scale target
>   run and take longer; nothing is capped silently. A capped `balanced`
>   profile and searching on a subsample are deferred, not in this phase.
> - **Fast profile (D12):** `profile="fast"` runs the linear model plus one
>   deep decision tree (unlimited depth, so that leakage shows as a large
>   effect), no grid, at most 2,000 rows, 200 resamples and shuffles. Under
>   time order the row cap keeps the most recent whole timestamps. Rows left
>   out by the cap are counted. If the capped rows hold too few timestamps to
>   form the holdout and the six blocks (a wide panel), the fast profile
>   stops with a named error telling the caller to use `full` (D20).
> - **Seeds and threads (D17):** one `seed` drives the split, the folds, every
>   model and every resample. `n_jobs` defaults to all cores and is recorded
>   in the output. The tool uses `threadpoolctl` so that `n_jobs` governs
>   every thread pool, and it holds linear algebra to one thread always. The
>   same seed must give the same result at any `n_jobs`. If you find that
>   cannot be achieved on this stack, report it and wait.

**What "broken but passes tests" looks like:**
> - **F1.** A fitted step sees the holdout. The model is refitted on all rows
>   before the holdout is scored, or an imputer, encoder, scaler or the leak
>   screen is fitted before the split. Pure noise shows skill.
> - **F2.** A column that copies the target, or is only filled in after the
>   outcome, is used as a feature. Skill is near 1 and is reported as
>   predictability.
> - **F3.** The headline is the best cross-validation score of the models
>   tried, not the holdout score.
> - **F4.** Accuracy is the headline on a rare class. Predicting the majority
>   scores 95% and that is presented as predictability.
> - **F5.** The task is misread. A target stored as 0 and 1 is treated as
>   regression, or an integer-coded target with a handful of values is
>   treated as continuous, and the headline is on the wrong scale.
> - **F6.** Something is lost without being reported, so the number covers
>   less than the user thinks: rows dropped for missing values, a numeric
>   column with a few text values turned all-missing or silently treated as
>   categories, a model family that raised an error and was skipped.
> - **F7.** Time order is ignored. Rows are shuffled despite a declared time
>   column, a training row is at or after the first holdout timestamp, the
>   gap is not applied, or the time column is misread so the rows are put in
>   the wrong order (a day-first date read month-first).
> - **F8.** Under time order, a trending or random-walk target is scored
>   against the training mean only. A model that has learned "today
>   resembles yesterday" is reported as high skill.

## Phase 1 — Design the gate FIRST

The gate is the harness. Everything else is support. Build it before anything else.

**The gate must catch the eight failure modes named above**, not merely
confirm the code runs. For a modelling tool, "it ran and wrote a JSON file
with numbers in it" is exactly what every failure mode above also does.

**How this gate observes the deliverable:**

| What is judged | Gate must |
|---|---|
| The modelling conclusion | run the tool on synthetic data with a known answer and assert the conclusion: skill found where it was planted, none found in noise, the leak excluded, no skill where only time-shuffling could produce it |
| Data handling | run the tool on small crafted tables and reconcile: rows in equal rows accounted for, every column accounted for, the holdout rows are the rows the scheme says they are |
| The output | read the files the tool wrote and assert every required part is populated, no NaN or infinity, and the result object equals the JSON |

The gate drives the tool through `python -m mlprofessor profile ...` with
`--profile fast`, in a new process per dataset, and reads `profile.json` and
`predictions.csv`. One check drives the Python function instead, through a
few lines of script run in a new process.

**Synthetic datasets, each generated from a fixed seed into
`verify/artifacts/data/` as CSV, about 1,500 rows each unless the band
measurements call for more:**

| Dataset | Built so that | The right conclusion |
|---|---|---|
| `signal_clf` | a binary target depends on two numeric features and one categorical feature, among several irrelevant columns | clear skill; every model family of the profile fitted |
| `signal_reg` | a numeric target is a known function of two features plus noise | clear skill |
| `noise_clf` | the target is a coin flip, independent of every feature | skill about zero |
| `noise_reg` | the target is drawn independently of every feature | skill about zero |
| `imbalanced` | pure noise with a 95/5 target | skill about zero; metric is ROC AUC with baseline 0.5 |
| `leak` | as `signal_clf`, plus `outcome_copy` (a noisy copy of the target), `settlement_amount` (filled only where the target is 1) and `strong_feature` (strongly predictive, not a leak) | both leak columns excluded and listed, each with its reason; `strong_feature` used; skill clear but not near 1 |
| `leak_reg` | as `signal_reg`, plus a column that is the target rescaled with a little noise | the column excluded and listed |
| `binary_numeric` | as `signal_clf`, with the target stored as the integers 0 and 1 | task is classification, decided by the rule; metric is ROC AUC |
| `ambiguous_target` | an integer target with 7 distinct values | the tool stops with the named error and writes no headline |
| `messy` | as `signal_clf`, with blank cells and `n/a` cells in features, 40 rows with no target, a few blank lines, a numeric column with a few text cells that pandas does not treat as missing (such as `abc` and `1,200`), a whole-number measure with every value distinct but not in order, a constant column, a consecutive identifier column, a free-text column and a date column | every count equals the gate's own count from the source; each column has the expected role and reason (the measure is a feature, the identifier is id-like); skill still clear |
| `time_blocks` | a time column; the label is random per block of about 20 consecutive timestamps; the features identify the block (constant within it, plus small noise) and carry nothing else | with `--time-col`: skill about zero, and the holdout is the latest rows. Under a shuffled split the same data shows high skill, which is what the broken F7 implementation must show |
| `time_dayfirst` | as `time_blocks`, with the time column written as day/month/year text | with `--time-col`: the tool stops with the named time-column error and writes no headline |
| `random_walk` | unique timestamps; the target is a random walk; the one feature is the target's previous value | with `--time-col`: the headline baseline is the previous value, and skill is about zero. Against the training mean alone the same data shows skill near 1 |

**Checks:**

| Check id | Catches | Dataset | Asserts |
|---|---|---|---|
| `data.rows_reconcile` | F6 | `messy` | rows loaded, dropped by reason, training and holdout in `profile.json` each equal the gate's own count from the source, and they add up |
| `data.columns_accounted` | F6 | `messy` | every source column appears exactly once, with the expected role and reason |
| `data.coercion_reported` | F6 | `messy` | the numeric column with text cells is used as numeric, its text cells are counted as coerced, its `n/a` cells are counted as missing, and a warning names it; it is not all-missing and not treated as categories |
| `models.all_accounted` | F6 | `signal_clf` | the models table lists every family of the profile, each with a status; none is absent |
| `task.binary_numeric` | F5 | `binary_numeric` | task is classification, decided by the rule; metric is `roc_auc` |
| `task.ambiguous_stops` | F5 | `ambiguous_target` | the tool exits non-zero naming the task error, and no headline is written |

*F1 has two forms of very different size. Refitting the model on all rows is a
large effect and the noise datasets catch it. A scaler or imputer fitted
before the split is too small an effect for any band; it is caught exactly, by
a structural test in the suite (see Phase 2). Use the large form for the F1
reference implementation.*

Requirements for the gate:

- **Built on `gatekit`.** One `@gate.check("area.what", catches=["F1"], doc=...)`
  per row above. Small checks with stable ids, because the task plan assigns
  each check to the task that must make it pass.
- **Every check names the failure mode it catches.** A check that catches
  nothing you can name is decoration; gatekit refuses it unless you give a
  written reason. The `why=` rows above carry theirs.
- **Synthetic ground truth, generated by the gate.** Each dataset is built in
  code from a fixed seed into `verify/artifacts/data/`. Prefer the standard
  library for generating the data and for the gate's own arithmetic (ROC AUC,
  squared error, counting rows), so the judge does not share a bug with the
  libraries the tool uses.
- **Never assert a score on real data.** There is no real data in this phase.
  Do not add any.
- **Scores are asserted as bands, and the bands are measured.** Use
  `ctx.require_between(value, low, high, label)`. To set a band: run the
  known-good reference implementation over at least five data seeds, take the
  observed range, add a margin, and confirm every broken implementation the
  check is meant to catch lands outside it on every seed. Write the measured
  ranges in a comment beside the band. A band you guessed is a threshold you
  invented. This brief contains no band on purpose. If two ranges overlap or
  nearly touch, fix the dataset, not the band.
- **The tool's own cut-offs are measured too, and are part of the spec, not
  the gate.** For each of the following, start from the value given, test it
  on the synthetic sets over the same seeds, pin the value you settle on in
  `spec.md`, and list it in your final report with the measurements, for my
  approval:
  - the leak rule: a single column's cross-validated skill on training rows
    of at least 0.98, or a column missing for more than 95% of one class and
    less than 5% of the other. It must flag `outcome_copy`,
    `settlement_amount` and the regression copy on every seed, and never flag
    `strong_feature`;
  - id-like (D19): a text column whose distinct values number more than 95%
    of the rows; or a whole-number column, judged by value so that blanks do
    not matter, in which every value is distinct and the values are either
    consecutive or strictly ordered in file order. Any other whole-number
    column stays a feature. Column roles are decided before the fast
    profile's row cap, so both profiles agree on them (D20);
  - numeric coercion: a text column in which at least 90% of the non-missing
    values parse as numbers is treated as numeric;
  - date-like (D22): a column with a datetime type, or a text column in
    which at least 95% of the non-missing values match one of a fixed list
    of date formats that you pin. Never pandas' lenient date parser, which
    accepts `1,200`, `May` and `09:30` as dates;
  - small holdout warning: fewer than 50 rows of the rarer class;
  - too small to profile: fewer than 100 usable rows;
  - no block-bootstrap interval: fewer than 20 distinct holdout timestamps;
  - autocorrelated panel target warning: lag-1 autocorrelation of the
    per-timestamp mean target above 0.8.
- **Deterministic.** Fixed seeds everywhere, and single-threaded inside the
  gate: pass `--n-jobs 1` on every run except the two that
  `output.same_at_any_n_jobs` compares, and set `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`
  and `MKL_NUM_THREADS` to 1 in the environment before the tool starts.
  Record every measured value with `ctx.record` or the band helpers:
  `--selftest` runs the good implementation twice and fails if anything moves.
- **A fast profile for the per-edit run.** The gate uses `--profile fast`.
  Run the tool at most once per dataset and configuration, lazily, and let
  the checks read the outputs: a per-edit run that selects three checks must
  start the tool only for the datasets those checks need. Mark
  `model.selection_full` `slow=True`, and any other check that still takes
  more than a few seconds. Use `ctx.fast` in setup to skip heavy preparation.
  Keep the per-edit run inside the budget `doctor` reports (20 seconds). The
  gate may start tool runs side by side to do so, at most 8 at once, each
  still single-threaded. The values must be identical to a sequential run;
  prove that once and say so in your report.
- **Through the public interface.** The command line and the documented
  function only. Never import internals; the builder is free to change those.
- **Binary.** Exit 0 = pass, non-zero = fail. No warnings tier, no partial credit.
- **Specific failure messages.** Not "score check failed" but "skill on
  `noise_clf` is 0.94, expected between the band limits: the model was
  refitted on rows that include the holdout, or the headline is a
  cross-validation score". The message is fed back to the builder; a vague
  message costs an iteration.
- **Reconciles independently.** The gate counts rows, finds the holdout rows
  and recomputes the metric itself from the source file. It never trusts a
  count or a score the tool reports.
- **Distinguishes harness failure from deliverable failure.** scikit-learn
  missing, `verify/artifacts/` not writable, or a dataset that failed to
  generate is `ctx.harness_error(...)`: exit 3, the words "HARNESS ERROR",
  and the code is NOT blamed. The tool exiting non-zero where it should have
  succeeded is a deliverable failure.
- **Writes only to `verify/artifacts/`.** Anything the gate writes elsewhere
  under `verify/` will be treated as tampering by the driver. Point the
  tool's `--out` at a folder under `verify/artifacts/` for every gate run.

**Standard layout — do not deviate:** the gate lives at `verify/smoke_test.py`,
takes the deliverable path (`mlprofessor`) as its argument, supports
`--selftest`, `--list`, `--only`, `--fast` and `--json` (gatekit provides all
five), and writes its datasets and any outputs to `verify/artifacts/`. A
consistent layout means the same driver and hooks work on every project.

**Then prove the gate works.** Register one `@gate.good_fixture`: a small,
correct implementation of both entry points (a package named `mlprofessor`
with the linear model and the deep tree is enough). For every failure mode,
register a `@gate.failure_mode` fixture: the same implementation, broken in
exactly that way and no other:

- `F1`: the chosen model is refitted on all rows before the holdout is scored
- `F2`: the leak screen is removed
- `F3`: the headline is the maximum of the cross-validation scores
- `F4`: the headline metric is accuracy
- `F5`: the task is decided from the column's type alone, so a numeric target is always regression
- `F6`: rows with any missing value are dropped before counting, with no entry in the accounting
- `F7`: the split is shuffled even when a time column is declared
- `F8`: the regression baseline is always the training mean

Then `--selftest`:

- passes the known-GOOD implementation on every check, twice, with identical values
- fails each known-BROKEN one, **on a check that names that failure mode**
- runs both from a temp dir and from the project dir, and reports if they
  disagree

The fixtures are reference implementations of the interface, a few dozen
lines each over a shared core. Writing them is also the first real test of
your interface contract: if the good one is awkward to write, the contract is
wrong.

Run the self-test. **A gate you have not watched fail is not a gate.** Do not
proceed until it discriminates correctly for all eight.

### `spec.md` — the contract
Concrete, not a template. It must contain:

- **The methodology, as decided above**, restated so that leakage is
  decidable from the text. The order of operations:
  1. load the table (D22); count the rows;
  2. drop rows with a missing target, and under time order rows with a
     missing time value; count each;
  3. under time order, read the time column in its accepted form (D18) and
     sort by it;
  4. decide the task (D4, D20);
  5. assign column roles that need no target: constant, id-like, datetime,
     free text, all missing, unsupported type (D19, D20);
  6. apply the fast profile's row cap, if any; count the rows left out;
  7. split off the holdout (D6 or D7), applying the gap;
  8. from here on, every fitted step sees training rows only: the leak
     screen, coercion statistics, imputation, encoding, scaling;
  9. select by 5 folds inside the training rows, refitting every
     preprocessing step inside each fold;
  10. refit the chosen configuration on all training rows;
  11. score it once on the holdout; score the baselines on the holdout;
  12. compute the interval and the p-value from the holdout predictions;
  13. assemble the result; write the files.

  A reader must be able to tell from the spec alone whether a given
  implementation leaks.
- **An interface contract:** the function signature and the meaning of each
  argument; the command line and its options; the exit codes; the full schema
  of `profile.json` (every key, its type and its meaning, covering `meta`,
  `input`, `rows`, `columns`, `task`, `validation`, `headline`, `baselines`,
  `cv`, `models`, `warnings`, `limitations`); the columns of
  `predictions.csv`; the columns of each DataFrame on `ProfileResult` and
  which part of the JSON each one equals; the warning codes; the names of the
  errors. Precise enough that someone could write tests against it without
  ever seeing the code, because that is exactly what happens next.
- **A seam for the tests.** The contract must define a documented way for a
  test to supply its own model family and its own preprocessing step, so a
  recording fake can prove which rows every fitted step received. Without it
  the small form of F1 cannot be tested.
- **The pinned values:** the grids (at most 8 combinations per family), the
  cut-offs you measured in Phase 1, the family order used for ties.
- **The facts from Phase 0** and the traps found there.
- **The loading rules (D22):** pandas' default missing-value tokens count as
  missing, never as coerced; the loader reads with `low_memory=False`; blank
  lines are not rows; duplicate column names stop with a named error and a
  blank header is kept under pandas' name with a warning. Say how each
  DataFrame-only type is treated (nullable integers, categories, booleans,
  datetimes). State as a limitation that a CSV is read with pandas' types,
  so text identifiers can lose leading zeros, and that a caller who needs
  control passes a DataFrame.
- **What happens at the edges.** Each one either raises a named error or is
  reported in the output. None is silently skipped:
  - the target column is absent, or has one distinct value;
  - a declared task the target does not support;
  - an ambiguous target under `task="auto"`;
  - no usable feature column;
  - too few rows to split;
  - a holdout or a fold with one class;
  - a time column that is not in an accepted form, or a gap that leaves no
    training rows;
  - duplicate column names; a blank header;
  - the fast profile on a panel too wide for its row cap;
  - too few holdout timestamps for the block bootstrap (interval absent,
    with a warning);
  - a model family that raises (status failed, error text kept, a warning);
    every family failing raises;
  - infinite values in a feature (treated as missing and counted);
  - exact duplicate rows (counted and reported, not dropped);
  - an unknown column type (excluded with the reason).
- **What is open.** The internal module layout; encoding and scaling details
  beyond "fitted on training rows only" and whatever you pin; the wording of
  the console summary. Say so, so the test author does not pin them down by
  accident.

Rules for the plan:

- **Every task is verifiable.** At least one gate check or test file. A task
